# Роли, пользователи и контроль доступа

## Модель учётных записей

В HR Automation есть два типа аккаунтов:

1. встроенный системный администратор `superadmin`;
2. обычный пользователь из таблицы `users`, обязательно связанный с одним сотрудником через `employee_id`.

`users.employee_id` уникален, поэтому у одного сотрудника не может быть нескольких обычных учётных записей.

Встроенный администратор хранится отдельно в `system_admin_accounts` и не является сотрудником.

## Superadmin

Заводские данные первого входа:

```text
login:    superadmin
password: superadmin
```

Если аккаунт всё ещё использует заводской hash/salt, миграция помечает его `must_change_password = 1`. После входа пользователь обязан установить постоянный пароль.

Особенности системного администратора:

- не связан с предприятием, отделом или сотрудником;
- имеет глобальный доступ к административным и HR-модулям;
- не имеет собственной карточки сотрудника;
- не удаляется и не блокируется через обычное управление пользователями;
- логин `superadmin` зарезервирован;
- системная роль `Superadmin` не назначается сотрудникам.

## Хранение паролей

Пароли не хранятся в открытом виде. Для каждого пароля используется отдельная соль и `scrypt`.

Для нового обычного пользователя требуется временный пароль. По умолчанию включается `must_change_password`, после чего пользователь обязан сменить его при первом входе.

Superadmin может сбросить пароль обычного пользователя. После сброса можно снова потребовать смену временного пароля.

## Роли

У обычного пользователя может быть несколько ролей.

Эффективный набор permissions является объединением permissions всех назначенных ролей. При этом scope вычисляется **отдельно для каждого permission**.

Это означает, например, что глобальное административное право не расширяет автоматически отделский доступ к сотрудникам.

Поддерживаемые scope:

- `global` — все данные системы;
- `enterprise` — данные предприятия пользователя;
- `department` — данные отдела пользователя;
- `self` — только собственные данные сотрудника.

## Системные роли

Системные роли создаются миграциями и защищены SQLite-триггерами. Их нельзя удалить, переименовать, поменять scope или вручную изменить набор permissions.

### Superadmin

- `global`;
- используется только встроенным системным аккаунтом;
- получает административный и HR-доступ ко всей системе;
- не получает `profile.view`, потому что не связан с сотрудником.

### Сотрудник

- `self`;
- просмотр собственной карточки;
- просмотр собственных отпусков;
- без права менять кадровые данные и отпуска.

Payroll/accounting permissions удалены из HR Core и в эту роль больше не входят.

### Руководитель предприятия

- `enterprise`;
- просмотр доступных HR-данных своего предприятия;
- системная роль соответствует фактическому `general_director_employee_id` предприятия.

При назначении нового руководителя роль автоматически добавляется его обычной учётной записи, если она уже существует. При снятии последнего соответствующего руководящего назначения роль автоматически отзывается.

Если учётная запись создаётся уже после назначения руководителем, backend сам добавляет обязательную системную роль.

### Руководитель отдела

- `department`;
- просмотр доступных HR-данных своего отдела;
- соответствует фактическому `director_employee_id` отдела.

Добавление и отзыв роли синхронизируются с фактическим руководящим назначением теми же правилами, что и для руководителя предприятия.

## Пользовательские роли

Superadmin или другая глобальная роль с `access.manage` может создавать кастомные роли.

Для роли задаются:

- название;
- описание;
- scope;
- permissions.

Правила backend:

- роль должна содержать минимум один permission;
- неизвестные permission-коды отклоняются;
- `employees.manage` автоматически требует `employees.view`;
- `organization.manage` автоматически требует `organization.view`;
- `recruitment.manage` автоматически требует `recruitment.view`;
- `vacations.manage` автоматически требует `vacations.view`;
- `access.manage`, `settings.manage` и `audit.view` требуют `global` scope;
- роль с `access.manage` также получает `employees.view`;
- системную роль нельзя редактировать или удалить;
- пользовательскую роль нельзя удалить, пока она назначена хотя бы одному пользователю.

## Пользователи-сотрудники

При создании обычной учётной записи указываются:

- активный сотрудник;
- уникальный username;
- временный пароль;
- статус `active` или `blocked`;
- одна или несколько ролей.

Username приводится к lower-case и должен соответствовать шаблону из латинских букв, цифр, точки, дефиса и подчёркивания.

Роль `Superadmin` в UI не предлагается и дополнительно запрещена backend-валидацией.

Если сотрудник становится неактивным, SQLite-триггер блокирует связанную обычную учётную запись.

## Актуальность сессии

Backend не доверяет набору permissions, который когда-то был выдан renderer-у. На каждом защищённом запросе `AuthenticationService` заново строит текущую сессию по состоянию БД.

Renderer также синхронизирует состояние:

- после HR/access-мутаций, которые потенциально могут изменить доступ;
- после восстановления backup;
- при возврате фокуса в окно;
- при возвращении вкладки/окна в visible state.

Если учётная запись стала недоступна, renderer завершает сессию. Если изменились роли или scopes, навигация и permission-aware UI обновляются без перезапуска приложения.

## Серверная авторизация

Проверки выполняются внутри Electron backend до вызова защищённых операций.

Проверяются:

- наличие активной сессии;
- обязательная смена временного пароля;
- наличие permission;
- scope именно этого permission;
- принадлежность конкретной записи разрешённой области;
- scope списков и фильтров;
- доступ к recruitment, vacations, dashboard и административным операциям.

UI скрывает недоступные действия, но это только UX. Основная защита находится в backend и SQLite.

## HR CRUD и scopes

Основные соответствия:

| Сущность | View | Manage |
| --- | --- | --- |
| предприятия / отделы / должности | `organization.view` | `organization.manage` |
| сотрудники / образование / опыт / кадровый журнал | `employees.view` | `employees.manage` |
| виды отпусков / отпуска | `vacations.view` | `vacations.manage` |

Особые правила:

- `employment_history` всегда read-only независимо от наличия `employees.manage`;
- изменение кадрового назначения, зарплаты, даты приёма и увольнение выполняются отдельными кадровыми командами;
- `vacation_types` можно читать с `vacations.view` из любого scope, но изменять только с global `vacations.manage`;
- изменение предприятий также требует глобальной области там, где операция затрагивает глобальную структуру;
- конкретная запись повторно проверяется на scope перед update/delete.

## Отпуска

`vacations.view` и `vacations.manage` ограничиваются сотрудниками доступной области.

Согласование фиксирует:

- дату;
- тип аккаунта;
- ID аккаунта;
- отображаемое имя согласовавшего.

После принятия решения запись защищается от изменения кадровых параметров. Удаление разрешено только для `planned`.

## Доступ к административным разделам

- `access.manage` — пользователи и роли, только global;
- `audit.view` — audit log, только global;
- `settings.manage` — backup/restore и административные настройки, только global;
- экспорт сотрудников требует глобального `employees.view`.

## Системные границы

Electron окно работает с:

- `sandbox: true`;
- `contextIsolation: true`;
- `nodeIntegration: false`.

Renderer получает только ограниченный `window.hrApi` через preload/contextBridge.

IPC handler дополнительно проверяет источник запроса. Входные данные валидируются Zod-схемами, а generic HR CRUD принимает только whitelisted сущности, поля и скалярные значения.

## Миграции RBAC

Ключевые этапы:

- `008_add_access_control.sql` — permissions, roles, users, user_roles и базовые guards;
- `009_refine_employee_role.sql` — уточнение системной роли сотрудника;
- `010_harden_access_lifecycle.sql` — защита lifecycle и руководящих назначений;
- `011_add_builtin_superadmin.sql` — отдельный встроенный системный аккаунт;
- `012_remove_accounting_scope.sql` — удаление payroll permissions и payroll-таблицы из HR Core;
- `014_stabilize_hr_core.sql` — обязательная смена заводского пароля, кадровые поля и дополнительные ограничения;
- `015_sync_leadership_roles.sql` — выдача руководящих системных ролей по фактическим назначениям;
- `016_restore_hr_core_guards.sql` — финальные guards организационной структуры.

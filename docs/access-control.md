# Роли, пользователи и контроль доступа

## Модель учётных записей

В HR Automation есть два типа аккаунтов:

1. встроенный системный администратор `superadmin`;
2. обычный пользователь из таблицы `users`, обязательно связанный с одним сотрудником через `employee_id`.

`users.employee_id` уникален, поэтому у одного сотрудника не может быть нескольких обычных учётных записей. Встроенный администратор хранится отдельно в `system_admin_accounts` и не является сотрудником.

## Superadmin

Заводские данные первого входа:

```text
login:    superadmin
password: superadmin
```

Если аккаунт всё ещё использует заводской hash/salt, миграция помечает его `must_change_password = 1`. После входа пользователь обязан установить постоянный пароль.

Особенности системного администратора:

- не связан с предприятием, отделом или сотрудником;
- имеет company-wide/global доступ;
- для операционных HR-разделов выбирает рабочее предприятие и, при необходимости, отдел;
- не имеет собственной карточки сотрудника;
- не удаляется и не блокируется через обычное управление пользователями;
- логин `superadmin` зарезервирован;
- системная роль `Superadmin` не назначается сотрудникам.

## Хранение паролей

Пароли не хранятся в открытом виде. Для каждого пароля используется отдельная соль и `scrypt`.

Для нового обычного пользователя требуется временный пароль. По умолчанию включается `must_change_password`, после чего пользователь обязан сменить его при первом входе. Superadmin может сбросить пароль обычного пользователя и снова потребовать смену временного пароля.

## Permissions и эффективный scope

У обычного пользователя может быть несколько ролей. Эффективный набор permissions является объединением permissions всех назначенных ролей, а scope вычисляется **отдельно для каждого permission**.

Поддерживаемые внутренние scope:

- `global` — company-wide доступ в пределах всей установки;
- `enterprise` — данные предприятия сотрудника;
- `department` — данные отдела сотрудника;
- `self` — только собственные данные сотрудника.

Наличие одного глобального permission не расширяет автоматически другой permission, выданный только на предприятие или отдел.

## Business Context

Одна установка HR Automation может обслуживать несколько предприятий. Для глобальных operational permissions используется Business Context:

1. пользователь выбирает предприятие;
2. при необходимости выбирает один отдел или оставляет «Все отделы»;
3. backend применяет выбранный контекст только к permissions, входящим в operational HR workspace.

Контекст доступен:

- встроенному `superadmin`;
- обычному пользователю с `global` scope и хотя бы одним operational HR-permission, поддерживающим Business Context.

При выбранном предприятии глобальный operational permission становится эффективным `enterprise`, а при выбранном отделе — `department`. Enterprise-level справочники, например изменение типов документов и видов отпусков, остаются enterprise-scoped даже при выбранном отделе.

Защита от «переезда» локальных полномочий:

- permission с исходным scope `enterprise` действует только в домашнем предприятии сотрудника;
- permission с исходным scope `department` действует только в домашнем отделе;
- выбор другого предприятия/отдела не переносит локальную роль в новый контекст;
- при отсутствии выбранного предприятия глобальные operational permissions временно неактивны на backend.

Реестр сотрудников намеренно остаётся company-wide/cross-enterprise для пользователя с глобальным `employees.view`. Это позволяет управлять кадровым составом всех предприятий из одного раздела, а операционные модули работают через выбранный Business Context.

## Системные роли

Системные роли создаются миграциями и защищены SQLite-триггерами. Их нельзя удалить, переименовать, поменять внутренний scope или вручную изменить набор permissions.

### Superadmin

- `global`;
- используется только встроенным системным аккаунтом;
- получает административный и HR-доступ ко всей установке;
- не получает `profile.view`, потому что не связан с сотрудником.

### Сотрудник

- `self`;
- доступ к собственной карточке и разрешённым self-функциям;
- без права менять кадровые данные.

### Руководитель предприятия

- `enterprise`;
- соответствует фактическому `general_director_employee_id` предприятия;
- роль синхронизируется с руководящим назначением.

При назначении нового руководителя роль автоматически добавляется его обычной учётной записи, если она уже существует. При снятии последнего соответствующего руководящего назначения роль автоматически отзывается. Если учётная запись создаётся уже после назначения, backend добавляет обязательную системную роль.

### Руководитель отдела

- `department`;
- соответствует фактическому `director_employee_id` отдела;
- добавление и отзыв роли синхронизируются с фактическим руководящим назначением.

### Администратор предприятия

- `enterprise`;
- операционное администрирование сотрудников, структуры, отпусков, подбора и других разрешённых модулей только внутри предприятия сотрудника;
- не превращается в администратора другого предприятия после кадрового перевода.

При изменении `employees.enterprise_id` системная роль `enterprise_admin` автоматически удаляется из `user_roles`. Новые полномочия в другом предприятии должны быть назначены явно.

### Администратор отдела

- `department`;
- операционное администрирование только внутри отдела сотрудника;
- при изменении `employees.department_id` системная роль `department_admin` автоматически отзывается.

## Пользовательские роли

Пользовательские роли — permission-only. Начиная с миграции `018_custom_roles_permission_only.sql`, для них не настраивается отдельная область данных: они хранятся с `scope_type = global`, а администратор роли определяет возможности путём включения/отключения конкретных permissions.

Backend проверяет:

- роль содержит хотя бы один permission;
- неизвестные permission-коды отклоняются;
- зависимости permissions нормализуются;
- системную роль нельзя редактировать или удалить;
- пользовательскую роль нельзя удалить, пока она назначена пользователю;
- пользователь не может делегировать permissions, которых нет у него самого, если операция выполняется не встроенным superadmin.

Глобальная пользовательская роль с operational HR-permissions получает Business Context и работает внутри выбранного предприятия/отдела. Платформенные административные permissions продолжают действовать глобально согласно их собственным правилам.

## Пользователи-сотрудники

При создании обычной учётной записи указываются:

- сотрудник;
- уникальный username;
- временный пароль;
- статус `active` или `blocked`;
- одна или несколько ролей.

Username приводится к lower-case и должен соответствовать backend-валидации. Роль `Superadmin` обычному сотруднику не назначается.

Если сотрудник становится неактивным, SQLite-триггер блокирует связанную обычную учётную запись.

## Кадровые переводы и права

Кадровый перевод может менять предприятие, отдел и должность сотрудника, но доступ не должен автоматически расширяться вслед за переводом.

Поэтому при изменении организационного назначения:

- out-of-scope пользовательские enterprise/department роли отзываются существующим DB guard;
- `enterprise_admin` отзывается при смене предприятия;
- `department_admin` отзывается при смене отдела;
- руководящие системные роли управляются отдельно через фактические поля руководителей предприятия/отдела.

Это разделяет кадровый факт «сотрудник переведён» и административный факт «сотруднику доверены права в новой области».

## Актуальность сессии

Backend не доверяет набору permissions, который когда-то был выдан renderer-у. На каждом защищённом запросе `AuthenticationService` заново строит текущую сессию по состоянию БД.

Renderer также синхронизирует состояние после мутаций, которые потенциально меняют доступ, и при возврате пользователя в приложение. Если учётная запись стала недоступна, renderer завершает сессию. Если изменились роли или scopes, навигация и permission-aware UI обновляются без перезапуска приложения.

## Серверная авторизация

Проверки выполняются внутри Electron backend до защищённых операций.

Проверяются:

- наличие активной сессии;
- обязательная смена временного пароля;
- наличие permission;
- scope именно этого permission;
- Business Context для operational permissions;
- принадлежность конкретной записи разрешённой области;
- scope списков и фильтров;
- доступ к recruitment, vacations, documents, analytics, dashboard и административным операциям.

UI скрывает недоступные действия, но это только UX. Основная защита находится в backend и SQLite.

## Организационные tenant-границы

Новые данные подчиняются следующим DB-инвариантам:

- сотрудник обязан иметь `enterprise_id`;
- отдел обязан иметь `enterprise_id`;
- должность обязана иметь `department_id`;
- существующий отдел нельзя «перепривязать» к другому предприятию;
- должность нельзя перенести между предприятиями;
- назначенный сотруднику отдел должен принадлежать его предприятию;
- назначенная должность должна принадлежать его отделу;
- табельный номер уникален в пределах предприятия, а не всей установки;
- email является контактным полем и не используется как глобальный uniqueness key.

## Исторический контекст предприятия

Текущее `employee.enterprise_id` меняется при переводе, поэтому исторические сущности хранят собственные snapshots:

- `employment_history.previous_enterprise_id/name`;
- `employment_history.new_enterprise_id/name`;
- `employee_documents.enterprise_id_snapshot/name_snapshot`;
- `vacations.enterprise_id_snapshot/name_snapshot`.

Snapshots создаются автоматически и не меняются вместе с текущим предприятием сотрудника. Это позволяет корректно отвечать на вопрос, в каком предприятии был оформлен документ, отпуск или кадровое событие.

## Отпуска

Актуальная модель отпусков использует granular permissions `vacations.*` и `vacation_types.*`.

Старый отдельный backend отпускных балансов/производственного календаря удалён:

- отсутствуют `leave.view`, `leave.manage`, `leave.calendar_manage`;
- отсутствуют таблицы `leave_balances`, `work_calendar_days`;
- отсутствуют `leave:*` IPC/preload API;
- отпускной реестр остаётся единственным operational источником отпускных записей.

## Системные границы Electron

Electron окно работает с:

- `sandbox: true`;
- `contextIsolation: true`;
- `nodeIntegration: false`.

Renderer получает только ограниченный `window.hrApi` через preload/contextBridge. IPC handlers дополнительно проверяют источник запроса. Generic HR CRUD принимает только whitelisted сущности, поля и скалярные значения.
